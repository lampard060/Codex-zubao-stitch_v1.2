# 足宝正式版技术架构与三端拆分方案

## 1. 目标

足宝正式版需要同时支撑三类使用场景：

- 商家端：门店后台管理，偏桌面与平板
- 技师端：工作台、收益、资料，偏手机
- 消费者端：预约、点钟、评价，强移动端

因此正式版架构目标不是“一个前端适配所有角色”，而是：

- 一套后端 API
- 三套前端体验壳
- 一套核心数据模型

## 2. 总体架构结论

## 2.1 推荐架构

- 前端：
  - `merchant-web`：商家端 Web / PWA
  - `technician-web`：技师端移动优先 Web / PWA
  - `consumer-web`：消费者端移动优先 Web
- 后端：
  - `api-server`：统一业务 API
- 数据：
  - `PostgreSQL`
- 部署：
  - 前端静态资源走站点域名
  - API 走 `api.zubao-cn.xyz`

## 2.2 为什么不建议三端共用一套页面结构

虽然三端可以共用：

- 登录态机制
- API
- 设计变量
- 部分基础组件

但不建议继续共用同一种页面组织方式，原因是：

- 商家端高频使用看板、列表、筛选、统计
- 技师端高频使用状态切换、收益查看、门店关系
- 消费者端高频使用浏览、预约、支付、评价

三端核心任务不同，直接影响：

- 导航方式
- 页面密度
- 首屏信息层级
- 按钮尺寸
- 交互链路长度

## 3. 三端拆分建议

## 3.1 商家端 `merchant-web`

### 定位

- 管理后台
- 以桌面为主，兼容手机和平板

### 适合的形态

- 响应式 Web
- 可加 PWA

### 推荐页面组织

- 左侧导航 + 主内容区（桌面）
- 手机端切换为顶部导航 / 抽屉导航

### 核心模块

- 首页
- 技师管理
- 订单管理
- 经营统计
- 工资管理
- 门店设置

### 重点要求

- 表格与列表必须支持移动端自动改卡片
- 所有筛选区需支持换行与折叠
- 统计面板需允许桌面双列、移动单列

## 3.2 技师端 `technician-web`

### 定位

- 手机优先的工作台
- 以技师个人任务完成为核心

### 适合的形态

- 移动优先 Web
- 强烈建议做 PWA

### 为什么适合 PWA

- 技师高频从手机打开
- 需要桌面图标入口
- 需要近似 App 的体验
- 以后可以做消息提醒、离线缓存、快捷访问

### 推荐页面组织

- 顶部标题 + 底部导航
- 单列布局
- 一屏只做一件主任务

### 核心模块

- 工作台
- 收益统计
- 我的资料

### 重点要求

- 所有核心操作按钮要大
- 不做复杂双栏
- 不做后台看板式布局
- 当前状态、门店关系、收益明细必须手机一屏能看清

## 3.3 消费者端 `consumer-web`

### 定位

- 预约与服务入口
- 几乎完全移动端

### 适合的形态

- 移动优先 Web
- 后期再评估微信小程序

### 核心模块

- 浏览门店
- 浏览技师
- 预约点钟
- 订单记录
- 评价

### 推荐页面组织

- 首页流式信息
- 底部导航
- 大卡片、短路径

### 后续演进建议

- Phase 3 前先做 H5 验证
- 确认消费者流量成立后，再决定是否补小程序

## 4. 前端代码组织建议

## 4.1 推荐目录

```text
apps/
  merchant-web/
  technician-web/
  consumer-web/
packages/
  ui/
  config/
  utils/
  api-client/
server/
  api/
```

## 4.2 各层职责

### `apps/merchant-web`

- 商家端页面与路由
- 商家专属布局
- 商家端组件组合

### `apps/technician-web`

- 技师端页面与路由
- 移动优先布局
- 技师专属状态卡、收益卡

### `apps/consumer-web`

- 消费者端页面与路由
- 预约、点钟、评价流程

### `packages/ui`

- 通用 Button / Input / Modal / Avatar / Badge
- 不放强角色耦合组件

### `packages/api-client`

- 所有前端共享的请求层
- Token 注入
- 错误处理
- 类型定义

### `server/api`

- 统一业务 API
- 权限控制
- 数据聚合
- 工资计算

## 5. 后端架构建议

## 5.1 核心原则

- API-first
- 前后端分离
- 服务端做权限
- 数据模型统一

## 5.2 推荐模块

- `auth`
- `shops`
- `technicians`
- `memberships`
- `applications`
- `orders`
- `analytics`
- `payroll`
- `profiles`

## 5.3 权限模型

### 商家

可以访问：

- 自己门店的数据
- 技师申请审核
- 本店订单
- 本店工资

不能访问：

- 其他门店数据
- 技师私人资料写权限

### 技师

可以访问：

- 自己的资料
- 自己的当前门店关系
- 自己的收益
- 自己参与的订单记录

不能访问：

- 其他技师数据
- 门店后台统计

### 消费者

后续开放：

- 浏览公开门店与技师资料
- 自己的预约与评价

## 6. 部署架构建议

## 6.1 当前可行结构

- `www.zubao-cn.xyz`：官网 / 演示站 / 后续消费者站点
- `api.zubao-cn.xyz`：统一 API

## 6.2 正式版建议

后面建议逐步拆成：

- `merchant.zubao-cn.xyz`
- `technician.zubao-cn.xyz`
- `www.zubao-cn.xyz`
- `api.zubao-cn.xyz`

这样更清楚：

- 商家端独立部署
- 技师端独立部署
- 官网 / 消费者入口独立部署
- API 独立服务

## 6.3 部署关系

```text
merchant.zubao-cn.xyz   -> merchant-web
technician.zubao-cn.xyz -> technician-web
www.zubao-cn.xyz        -> 官网 / consumer-web
api.zubao-cn.xyz        -> api-server
                         -> PostgreSQL
```

## 7. 正式开发建议

## 7.1 第一阶段

- 先做 `merchant-web + api-server + PostgreSQL`
- 技师端先做最小可用页面

原因：

- 商家端是 Phase 1 核心付费能力
- 订单、工资、统计都以商家端为中心

## 7.2 第二阶段

- 补齐 `technician-web`
- 接收益、资料、门店关系 API

## 7.3 第三阶段

- 再做 `consumer-web`
- 再接预约与评价

## 8. 当前项目与正式版的关系

当前静态原型：

- 可以继续作为视觉和交互参考
- 不建议直接在这一套 HTML 上硬改到正式版

正式版更建议：

- 重建为多应用前端结构
- 抽共享设计系统和 API 层
- 保留现有页面作为 UI 参照物

## 9. 最终结论

- 当前后端方向是正确的：一套 API + 一套数据库
- 当前前端原型不适合直接演进成“三端共用壳”
- 正式版应采用“三端拆分、一套后端”的方案
- 技师端和消费者端必须移动优先
- 商家端可以保留后台感，但必须保证移动端可用
